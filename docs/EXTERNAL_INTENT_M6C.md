# M6C — External Intent Binding + Approval UX Contract

M6C completes the platform-neutral M6 tool/authority path. It translates an untrusted VN97
cognition proposal into an exact M6A action request and an explicit human-approval session
without giving the cognition model any authority-bearing primitive.

## End-to-end boundary

`CognitionLoop → WAITING_EXTERNAL → VN97 external intent → ExternalIntentBinder
→ exact ExternalActionRequest → ApprovalPrompt → explicit UI decision
→ ApprovalToken → M6A gate/lease/audit → M6B handler → PlanController`

The model can propose intent. Trusted runtime code owns every authority transition.

## Trusted capability catalog

`ExternalIntentBinder` accepts an explicit tuple of allowed capability IDs only after the
`TypedCapabilityRegistry` is sealed. For each ID it exposes a read-only
`ExternalCapabilityView` containing:

- capability ID;
- required scope keys;
- optional scope keys;
- descriptor-level approval requirement;
- bounded maximum payload bytes.

Policy grants, concrete allowed scope values, approval secrets, existing approvals, leases and
handler objects are not included in the cognition request.

## VN97 cognition operation

`VN97CognitionAdapter.propose_external_intent()` uses the same strict VN97COG1 envelope as M5C.
The model must return exactly:

`{"capability_id":"...","scope":{"key":"string"},"payload":{...}}`

Scope values must be non-empty strings. Payload must be one strict JSON object. Duplicate keys,
wrappers, extra fields, non-finite constants and malformed shapes fail closed.

The model does **not** emit plan ID, step ID or objective as trusted output.

## Exact request binding

Before calling cognition, the binder snapshots the single active `WAITING_EXTERNAL` step. The
final `ExternalActionRequest` always takes these fields from the trusted planner:

- `plan_id`;
- `step_id`;
- immutable step `objective`.

Only capability ID, scope and payload come from the untrusted intent, and those are revalidated
against the sealed registry descriptor.

After model inference returns, the binder reads the planner boundary again. If the snapshot has
changed, the intent is stale and binding fails closed. Therefore an intent produced for one step
cannot be silently rebound to a later external step.

## Approval UX contract

`ExternalApprovalCoordinator` holds the trusted `ApprovalAuthority`. It creates an
`ApprovalPrompt` bound to:

- principal;
- exact request digest;
- plan/step/objective;
- capability ID;
- exact canonical scope;
- exact canonical payload;
- creation and expiry times.

`presentation_json` is generated by trusted code from those exact fields. A platform UI may
render it differently, but it must not change the request being approved.

Approval sessions are bounded, time-limited, thread-safe and one-shot. Resolving a prompt removes
it before token minting. Consequences:

- denial returns no token;
- expiry returns no token;
- a fabricated/tampered prompt is rejected;
- a stale prompt is rejected;
- repeated approval is rejected;
- simultaneous double-click/callback races mint at most one token.

The coordinator also bounds prompt TTL, approval-token TTL and the number of pending prompts.

## What cognition cannot do

M6C intentionally provides no model API for:

- creating or changing `PolicyGrant` values;
- obtaining the approval HMAC secret;
- minting `ApprovalToken` values;
- issuing/consuming `CapabilityLease` values;
- accessing capability handlers directly;
- changing the planner fields bound into the request.

A valid intent can still be denied later by M6A exact-scope policy or approval validation.

## Android handoff

M6C defines the approval data/lifecycle contract, not Android UI implementation. M7 must supply:

- Android approval presentation;
- process/lifecycle restoration rules;
- Keystore-backed approval secret protection;
- platform permission brokers;
- concrete `AppDeviceAdapter`.

Those implementations must preserve exact-request binding and may not treat notification/UI
interaction itself as authority unless it resolves the active trusted approval session.

## Verification

Regression coverage includes:

- sealed registry requirement;
- exact trusted planner binding;
- catalog and capability-schema enforcement;
- no policy/approval/lease exposure to cognition;
- stale-step race rejection;
- one-shot approval and exact request digest verification;
- denial and expiry;
- tampered prompt rejection;
- concurrent resolution minting at most one token;
- pending prompt bounds and expiry pruning;
- full M6C → M6A → planner execution;
- strict VN97COG1 external-intent parsing.
